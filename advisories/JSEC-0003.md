# JSEC-0003 — Unrestricted upload of SHTML and other executable files

| | |
|---|---|
| **CVE** | CVE-2026-73373 |
| **Upstream advisory** | [20260810](https://developer.joomla.org/security-centre/1077-20260810-core-unrestricted-uploads-of-shtml-files.html) · [GHSA-38c6-5ffm-cv2j](https://github.com/advisories/GHSA-38c6-5ffm-cv2j) |
| **Severity** | High (upstream rating) |
| **Affected** | Joomla 1.0.0 – 5.4.7, 6.0.0 – 6.1.2 |
| **Verified on** | Joomla 3.10.12 — **confirmed vulnerable** |
| **File** | `libraries/src/Filter/InputFilter.php` |
| **Patch** | `patches/0003-*.patch` |

## The vulnerability

`InputFilter::isSafeFile()` is the gate every core upload path runs through. Its
default list of forbidden extensions in 3.10.12 was:

```php
'forbidden_extensions' => array(
    'php', 'phps', 'pht', 'phtml', 'php3', 'php4', 'php5', 'php6', 'php7',
    'php8', 'phar', 'inc', 'pl', 'cgi', 'fcgi', 'java', 'jar', 'py',
),
```

PHP, Perl and CGI are covered. **Server-parsed HTML is not.** On a server with
`mod_include` enabled and an `AddHandler`/`AddOutputFilter` mapping for `.shtml` —
a common default on older Apache and shared hosting — an uploaded file containing:

```html
<!--#exec cmd="id" -->
```

is executed by the web server when fetched. Classic ASP (`.asp`, `.aspx`) is
similarly absent, which matters on IIS.

This is the oldest issue in the set: the upstream advisory lists it as affecting
Joomla **1.0.0** onward.

## Proof

From `tests/probe.php` against stock 3.10.12. Each case writes a file containing an
SSI `exec` directive and asks `isSafeFile()` whether it may be uploaded:

```
CVE-2026-73373/shtml                         VULNERABLE  allowed
CVE-2026-73373/shtm                          VULNERABLE  allowed
CVE-2026-73373/sht                           VULNERABLE  allowed
CVE-2026-73373/stm                           VULNERABLE  allowed
CVE-2026-73373/asp                           VULNERABLE  allowed
CVE-2026-73373/aspx                          VULNERABLE  allowed
CVE-2026-73373/php                           FIXED       blocked
CVE-2026-73373/control-jpg-allowed           FIXED       allowed
```

The last two lines are controls: `.php` was already blocked, and a benign `.jpg`
must stay uploadable. After the patch, all six hostile extensions report `blocked`
and the `.jpg` control still reports `allowed`.

## Exploitability

Of the four issues in this set, this is the one that most plausibly leads to code
execution on a real site, and it is the one to apply first. It requires two things:

1. An upload path reachable by the attacker. An authenticated contributor using the
   media manager is the straightforward case; some third-party extensions expose
   uploads to lower privilege levels or to guests.
2. A web server that executes the extension. This is **configuration-dependent** — on
   a server with no SSI handler and no ASP, an uploaded `.shtml` is inert text.

Check your own server before deciding how urgent this is. On Apache, look for
`Options +Includes` and any `AddHandler server-parsed` / `AddOutputFilter INCLUDES`
directive covering `.shtml`. A hardened `.htaccess` that denies execution in the
upload directory is a good independent mitigation and worth having regardless of
this patch.

## The fix

Replace the list with the full set upstream now keeps as
`InputFilter::FORBIDDEN_FILE_EXTENSIONS` in Joomla 5.4.9:

```php
'forbidden_extensions' => array(
    'asp', 'aspx', 'cgi', 'fcgi', 'inc', 'jar', 'java', 'phar', 'php', 'php3', 'php4', 'php5', 'php6',
    'php7', 'php8', 'php9', 'phps', 'pht', 'phtml', 'pl', 'py', 'sht', 'shtm', 'shtml', 'stm',
),
```

Net additions over 3.10.12: `asp`, `aspx`, `php9`, `sht`, `shtm`, `shtml`, `stm`.
Nothing is removed.

### Deviation from upstream

Upstream promoted the list to a class constant. The backport keeps it inline in the
`$defaultOptions` array, because 3.10 code and third-party extensions override
`forbidden_extensions` by passing options to `isSafeFile()`, and introducing a
constant that nothing in the 3.x tree references would be churn without benefit.

## Behaviour change

This is deliberately a behaviour change, not a transparent fix. A site that
legitimately accepts any of the newly-blocked extensions through an upload form will
start rejecting them.

The correct response is to override the option at that call site:

```php
InputFilter::isSafeFile($file, array('forbidden_extensions' => array(/* your list */)));
```

Do not revert the patch to restore the old behaviour globally.
