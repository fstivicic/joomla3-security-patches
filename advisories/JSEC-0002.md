# JSEC-0002 — Unauthorised user account creation via profile.save

| | |
|---|---|
| **CVE** | CVE-2026-90907 |
| **Upstream advisory** | [20260902](https://developer.joomla.org/security-centre/1082-20260902-core-unauthorized-user-account-creation-via-profile-save-controller.html) · [GHSA-j6fq-w4r3-5q3g](https://github.com/advisories/GHSA-j6fq-w4r3-5q3g) |
| **Severity** | Medium (upstream rating) |
| **Affected** | Joomla 1.5.0 – 5.4.8, 6.0.0 – 6.1.3 |
| **Verified on** | Joomla 3.10.12 — **confirmed vulnerable** |
| **File** | `components/com_users/controllers/profile.php` |
| **Patch** | `patches/0002-*.patch` |

## The vulnerability

`UsersControllerProfile::save()` checks the CSRF token and then does this:

```php
$this->checkToken();

$app    = JFactory::getApplication();
$model  = $this->getModel('Profile', 'UsersModel');
$user   = JFactory::getUser();
$userId = (int) $user->get('id');

// Get the user data.
$requestData = $app->input->post->get('jform', array(), 'array');

// Force the ID to this user.
$requestData['id'] = $userId;
```

There is no check that anyone is logged in. For a guest, `JFactory::getUser()`
returns a guest object whose `id` is `0`, so `$requestData['id'] = 0`. The profile
model treats an id of zero as "no existing record" and **stores a new user**.

The result is account creation on a site that has registration disabled — the
`com_users` "Allow User Registration" setting is bypassed entirely, because that
setting governs the registration controller, not this one.

The sibling `edit()` method in the same class *does* guard itself, comparing the
requested `user_id` against the logged-in id. `save()` was simply missed.

## Proof

Running the controller needs a full CMS application and a database, so the probe
performs a structural check on `save()` instead: is there a guest guard, and does it
sit before the `jform` data is read?

```
CVE-2026-90907/profile-save-guest-guard      VULNERABLE  no guard
```

After the patch:

```
CVE-2026-90907/profile-save-guest-guard      FIXED       guard precedes form read
```

This is weaker evidence than the runtime proofs for the other three issues, and it is
labelled as such. It confirms the code shape the advisory describes and confirms the
patch changes it; it does not execute the attack. If you want end-to-end
confirmation, reproduce on a staging site with registration disabled by posting a
valid token plus a `jform` payload to `index.php?option=com_users&task=profile.save`
while logged out, then check `#__users` for a new row.

## Exploitability

The CSRF token requirement is not a meaningful barrier: tokens are available in the
HTML of ordinary front-end pages, so an attacker can fetch a page, read the token,
and post. The practical limits are different:

- The created account lands at whatever group the model assigns by default, typically
  the lowest-privilege registered group — hence upstream's Medium rather than High.
- Form validation still applies, so the payload must satisfy the profile form's
  required fields.

The realistic harm is bypassing a deliberate "no public registration" policy: spam
accounts, enumeration of a members-only site, and whatever a site grants its lowest
registered tier. On a site that already allows open registration, this changes very
little.

## The fix

Add the guard upstream added in 5.4.9, before any request data is read:

```php
// Only allow logged in users. A guest reaching this point would be saved as a
// new record because $userId is 0, creating an account without registration.
if ($user->get('guest'))
{
    $app->enqueueMessage(JText::_('JERROR_ALERTNOAUTHOR'), 'error');
    $app->setHeader('status', 403, true);

    return false;
}
```

### Deviations from upstream

Upstream throws `new \RuntimeException(Text::_('JERROR_ALERTNOAUTHOR'), 403)`. The
backport enqueues the message and sets a 403 header instead, which is how the
`edit()` method in this same 3.10 class already rejects an unauthorised request. The
outcome is identical — the save is refused before any data is read — and matching the
file's existing convention keeps the diff to one hunk and avoids introducing
Joomla 4 error-handling behaviour into a 3.x controller.

`JERROR_ALERTNOAUTHOR` is an existing core language string in 3.10, so no language
file changes are needed.

## Behaviour change

None for legitimate users. A logged-in user saving their own profile is unaffected;
only guests reaching `profile.save` are now refused.
