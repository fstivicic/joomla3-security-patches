## The vulnerability

`InputFilter::checkAttribute()` decides whether an HTML attribute carries a dangerous
URL scheme. In 3.10.12 it did this:

```php
$quoteStyle = version_compare(\PHP_VERSION, '5.4', '>=') ? \ENT_QUOTES | \ENT_HTML401 : \ENT_QUOTES;

$attrSubSet[0] = strtolower($attrSubSet[0]);
$attrSubSet[1] = html_entity_decode(strtolower($attrSubSet[1]), $quoteStyle, 'UTF-8');

return (strpos($attrSubSet[1], 'expression') !== false && $attrSubSet[0] === 'style')
    || preg_match('/(?:(?:java|vb|live)script|behaviour|mocha)(?::|&colon;|&column;)/', $attrSubSet[1]) !== 0;
```

Three independent problems let a payload through:

**1. The entity table is HTML 4.01, not HTML5.** `ENT_HTML401` does not know
HTML5-only named entities such as `&Tab;` and `&NewLine;`, so they survive decoding
as literal text. The regex then looks for `javascript:` in a string that still reads
`java&Tab;script:` and finds nothing. A browser resolves the entity and executes it.

**2. It lowercases before decoding.** PHP's entity tables are case sensitive.
`strtolower()` turns `&NewLine;` into `&newline;`, which is not a valid entity in any
table, so even switching to `ENT_HTML5` would not have helped while the lowercasing
came first. The order of these two operations is itself the bug.

**3. It never normalised whitespace.** `html_entity_decode()` does resolve a properly
terminated numeric reference like `&#10;`, but the result is a literal newline inside
the string — so `java&#10;script:` decoded to `java\nscript:`, which the regex again
does not match, while a browser strips the control character and runs it.

The same forgiveness applies to unterminated references: browsers consume
`java&#10script:` and `java&#x0Ascript:`, PHP's decoder does not.

## Proof

From `tests/probe.php` against stock 3.10.12. `checkAttribute()` returns `true` when
it recognises a value as hostile, so `bypass` means it returned `false`:

```
CVE-2026-92231/html5-entity-tab              VULNERABLE  bypass
CVE-2026-92231/html5-entity-newline          VULNERABLE  bypass
CVE-2026-92231/unterminated-numeric          VULNERABLE  bypass
CVE-2026-92231/unterminated-hex              VULNERABLE  bypass
CVE-2026-92231/terminated-numeric            VULNERABLE  bypass
CVE-2026-92231/literal-whitespace            VULNERABLE  bypass
CVE-2026-92231/plain-control                 FIXED       detected
```

The last line is the control: plain `javascript:alert(1)` was always caught, which is
why this went unnoticed. After the patch, all seven report `detected`.

## Exploitability — read this before prioritising

The filter bypass is real and reproducible at the unit level. **Its end-to-end impact
is not demonstrated.** In both configurations tested — a blacklist filter with
`xssAuto` enabled, and a whitelist filter explicitly permitting `<a href>` —
`InputFilter::clean()` dropped the hostile anchor anyway, through attribute handling
unrelated to this check.

So on the evidence gathered here, this is a **defence-in-depth failure** rather than a
proven injection path: a security control that was not doing its job, in a codebase
where something else happened to catch the payload. That is still worth patching —
the next caller, or a different filter configuration, may not be so lucky, and
upstream rated it High — but it is not evidence of an exploitable hole in a default
Joomla 3 site, and this advisory will not claim otherwise.

If you can construct an end-to-end exploit through `clean()`, please open an issue;
that materially changes the priority.

## The fix

Backported from the current `joomla-framework/filter` package. Decode first, with the
HTML5 entity table, then resolve unterminated numeric references, and only then
lowercase and strip whitespace before matching:

```php
$quoteStyle = defined('ENT_HTML5') ? \ENT_QUOTES | \ENT_HTML5 : \ENT_QUOTES;
$decoded    = html_entity_decode($attrSubSet[1], $quoteStyle, 'UTF-8');

$decoded = preg_replace_callback(
    '/&#(x[0-9a-f]+|[0-9]+);?/i',
    array(__CLASS__, 'decodeNumericReference'),
    $decoded
);

$attrSubSet[1] = strtolower($decoded);
$attrSubSet[1] = str_replace(array("\t", "\n", "\r", " ", "\0", "\v", "\f"), '', $attrSubSet[1]);
```

### Deviations from upstream

Two, both to keep the 3.10 branch's PHP floor:

- Upstream uses an anonymous `static function` for the decode callback. Static
  closures are PHP 5.4+, and Joomla 3.10 supports 5.3.10, so the callback is a named
  `public static` method, `decodeNumericReference()`. This adds one public method to a
  vendored framework class.
- Upstream calls `mb_chr()` unconditionally; that needs PHP 7.2 and the mbstring
  extension. The backport guards it with `function_exists()` and falls back to
  `html_entity_decode('&#' . $codepoint . ';', ...)`, which resolves a terminated
  numeric reference without mbstring.

`ENT_HTML5` is itself PHP 5.4+, so it is feature-detected. On PHP 5.3 the named-entity
half of the fix degrades to the old table, while the numeric-reference and
whitespace-stripping halves still apply.

## Behaviour change

Attribute values are now whitespace-stripped before the scheme check. A value that
genuinely contains `java script:` — in a `title` attribute, say — is treated as
hostile and the attribute is dropped. Upstream accepted this trade-off and so does
this backport.
