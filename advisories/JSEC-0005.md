## Why this is here when the advisory says 4.0.0+

This advisory was listed as unresolved in an earlier revision of this repository
because two authoritative sources disagreed. That is now settled, and the answer is
more interesting than either source suggested.

The Joomla security centre *listing* appeared to show a lower bound of 3.0.0; the
advisory *detail page* and the GitHub advisory both say 4.0.0. The detail page is
correct as a statement of what Joomla assessed — but **Joomla does not assess EOL
branches at all**, so "4.0.0 and later" describes the scope of their review, not the
extent of the bug.

Checked directly against the source: the vulnerable pattern is present in 3.10.12,
the enabling validator default is present in 3.10.12, and the dangerous schemes are
demonstrably accepted. Three of the four fields upstream fixed exist here in
identical form.

The published range was the wrong question. The code was the right one.

## The vulnerability

Three core form fields carry a URL that Joomla later fetches **server-side**:

| Extension | File | Field |
|---|---|---|
| com_newsfeeds | `administrator/components/com_newsfeeds/models/forms/newsfeed.xml` | `link` |
| mod_feed (site) | `modules/mod_feed/mod_feed.xml` | `rssurl` |
| mod_feed (admin) | `administrator/modules/mod_feed/mod_feed.xml` | `rssurl` |

Each declared `filter="url" validate="url"` and **no `schemes` attribute**. When the
attribute is absent, `UrlRule` falls back to a very broad list:

```php
$scheme = array('http', 'https', 'ftp', 'ftps', 'gopher', 'mailto', 'news', 'prospero',
    'telnet', 'rlogin', 'sftp', 'tn3270', 'wais', 'mid', 'cid', 'nntp', 'tel', 'urn',
    'ldap', 'file', 'fax', 'modem', 'git');
```

`file`, `gopher`, `ldap` and `telnet` are all accepted.

The stored value then reaches `FeedFactory::getFeed()`, which does this **before** any
HTTP client is involved:

```php
$reader = new \XMLReader;

if (!@$reader->open($uri, null, LIBXML_NOERROR | LIBXML_ERR_NONE | LIBXML_NOWARNING))
{
    // ... only now fall back to HttpFactory
}
```

`XMLReader::open()` resolves its argument through **PHP's stream wrappers**, not an
HTTP client. That is what makes this more than ordinary SSRF:

- `file:///etc/passwd` is a **local file read**. Any XML-parseable file readable by the
  web server can be pulled into the feed output.
- `gopher://host:port/_PAYLOAD` gives an attacker control of the bytes written to an
  arbitrary TCP port — the classic pivot to an unauthenticated Redis or SMTP service
  on localhost.
- `http://169.254.169.254/...` reaches cloud instance metadata.
- `php://`, `compress.zlib://` and any other registered wrapper are equally in scope.

The `@` suppression means failures are silent, which makes blind probing comfortable.

## Proof

From `tests/probe.php` against stock 3.10.12. The notes section exercises `UrlRule`
directly; the findings check each affected manifest:

```
CVE-2026-92222/com_newsfeeds                 VULNERABLE  link (no schemes)
CVE-2026-92222/mod_feed-site                 VULNERABLE  rssurl (no schemes)
CVE-2026-92222/mod_feed-admin                VULNERABLE  rssurl (no schemes)
CVE-2026-92222/control-https-accepted        FIXED       legitimate feed URL

Notes:
  CVE-2026-92222/urlrule-default-file        accepted for a field declaring no schemes attribute
  CVE-2026-92222/urlrule-default-gopher      accepted for a field declaring no schemes attribute
  CVE-2026-92222/urlrule-default-ldap        accepted for a field declaring no schemes attribute
```

After the patch all three fields report `scheme-constrained`, and the control confirms
an ordinary `https://` feed URL is still accepted.

## Exploitability

This needs an authenticated user, but not an administrator:

- **mod_feed** requires module edit rights — Manager or above by default.
- **com_newsfeeds** requires create or edit rights on news feeds, which sites
  routinely delegate to editor-level groups.

So on a multi-author site this is a privilege escalation: someone trusted to add a
news feed gains local file read and the ability to send crafted bytes to internal
services. That is consistent with upstream's High rating despite the authentication
requirement.

It is **not** reachable by an anonymous visitor in a default configuration.

## The fix

Add the scheme constraint upstream added, to each of the three fields:

```xml
 			required="true"
 			filter="url"
 			validate="url"
+			schemes="http,https"
 		/>
```

No code change is needed: **3.10's `UrlRule` already implements the `schemes`
attribute**, it was simply never used on these fields.

```php
if ($element['schemes'] == '')
{
    $scheme = array(/* the long permissive list */);
}
else
{
    $scheme = explode(',', $element['schemes']);
}
```

### Difference from upstream

Upstream's change set covers a fourth file, `plugins/task/requests/forms/get_requests.xml`.
That has no analogue here — the Task Scheduler was introduced in Joomla 4.1 and
`plugins/task/` does not exist in 3.10. Nothing is missing from this backport.

## Limitations — important

**Restricting the scheme does not stop SSRF over HTTP.** After this patch,
`http://169.254.169.254/latest/meta-data/` and `http://127.0.0.1:8080/admin` are still
valid feed URLs, and Joomla will still fetch them. The probe records this explicitly:
the `control-https-accepted` case and an internal-address URL are both accepted by
design.

This matches upstream, which also did not add internal-address filtering. Blocking
private address ranges would break the legitimate and common case of an intranet feed,
and cannot be done correctly in a form validation rule anyway — DNS rebinding and
redirects defeat it. If HTTP SSRF to internal hosts matters in your environment, the
controls that actually work are egress firewall rules or an outbound proxy allowlist,
not a Joomla patch.

**The fix is input-time only.** It prevents a hostile value being *saved* through the
form. It does not sanitise a value already stored in the database, or one written by
another route (direct SQL, a migration, a third-party extension). After applying,
audit existing values:

```sql
SELECT id, name, link   FROM #__newsfeeds WHERE link   NOT LIKE 'http://%' AND link   NOT LIKE 'https://%';
SELECT id, title, params FROM #__modules  WHERE module = 'mod_feed';
```

The second needs manual inspection — `rssurl` lives inside the JSON `params` column.

A fetch-time scheme check in `FeedFactory::getFeed()` would close that gap, and is a
reasonable hardening, but it is not what upstream did and it is not included here. See
`advisories/NOT-APPLICABLE.md` for the policy on going beyond reviewed upstream fixes.
